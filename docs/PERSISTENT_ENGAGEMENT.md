# Persistent Engagement v1

База: `376ffc3f31e4ed1d94821129b1d33fed5ba25a43`, репозиторій `derfasis/HARNES2`.
Статус: реалізований локальний increment для інтеграції та перевірки у штатному середовищі, не production certification.

## Архітектурне рішення

Це не другий cognitive runtime і не новий агент. `BusinessService` залишається єдиною
транзакційною межею команд; SQLite залишається source of truth. `EngagementLoop`
реалізує бізнес-переходи, використовує існуючі tasks, runs, drafts, approvals,
delivery_attempts, outcome_events і lessons. `Scheduler` вирішує, коли запускати
наявний Hermes runtime, але не запускає його просто тому, що минув ще один tick.

Єдина канонічна модель ownership залишається `conversations.ownership`.
`engagements.status=HUMAN` відображає стан справи, а не створює другого незалежного
власника. Передача через HANDOFF одразу ставить HUMAN_OWNED та скасовує AI-роботу;
прийняття оператором записується окремо. Повернення здійснюється тільки через явне
рішення оператора. Інтерфейс є однокористувацьким, як і вихідний застосунок;
`operator` тут означає локального автентифікованого власника, не нову систему RBAC.

Межа v1: одна активна справа на розмову. Після завершення можна явно відкрити нову
справу, стара історія не переписується. Одночасні теми, зв’язування особи між каналами
та багатокористувацьке призначення операторів свідомо відкладені.

## Що є чим

| Об’єкт | Реалізація і межа істинності |
| --- | --- |
| Observation | Існуюче messages/source evidence. Запис повідомлення доводить, що його отримано або засвідчено оператором, не правдивість тексту. |
| Claim | `engagement_beliefs.kind=CLAIM`: точна цитата з inbound, посилання на повідомлення обов’язкове. |
| Hypothesis | `HYPOTHESIS`: інтерпретація з evidence, counterevidence, строком актуальності та supersession. Не потрапляє в legacy facts. |
| Verified fact | `VERIFIED_FACT`: тільки оператор із полем verification. Це засвідчена оператором перевірка; система не гарантує істинність зовнішнього світу й не верифікує джерело автоматично. |
| Decision | Запис тригера, версій контексту, evidence snapshots, стислої причини, очікуваного наступного стану й стратегії. Не прихований chain of thought. |
| Commitment | Proposed до доставки вихідної версії тексту; open лише після підтвердженої доставки або явного операторського запису з реальною цитатою. |
| Action | `engagement_actions` зв’язує ACT з конкретним draft і типізованим дозволом. Не є відправленням. |
| Outcome | Існуючий outcome_events. Зв’язок decision_outcomes є спостережуваною асоціацією, а не доведеним причинним внеском AI. |
| Lesson | Candidate в існуючих lessons; структуровані evidence/counterexample episodes та окремий operator review. |
| Strategy | Незмінна версія локальної інструкції після review. Не зміна identity, policy, permissions або коду. |

Legacy `facts.status=confirmed` не мігрують автоматично в VERIFIED_FACT. Legacy
permission strings не стають типізованими grants. Жоден старий outcome не стає
автоматично приписаним AI результатом.

## Реальні переходи

`engagement.open` скасовує стару увагу і робить старі pending/approved drafts stale.
Відкриття заборонено, якщо є sending/delivery_unknown. Можна явно ввімкнути
`engagement.enabled=true` для створення справи на новому inbound, але цей прапор
за замовчуванням false. Закриті або STOPPED справи ніколи не воскресають автоматично.

Модель отримує актуальну справу, active beliefs, unknowns, delivered quotes,
зобов’язання, очікування, handoff і локальні стратегії. Вона може спершу запропонувати
beliefs, потім прийняти одне рішення з `expected_revision`. Зміна business context
скасовує running attention, робить попереднє рішення stale і блокує його виконання.
Рішення після власного HANDOFF/STOP також стає stale як джерело права на подальше
виконання, але залишається історичним рішенням. Status не означає, що рішення було
хибним, а delivery/outcome не виводяться з цього status.

| Рішення | Ефект |
| --- | --- |
| ACT | Атомарно зберігає рішення, pending draft, точний grant та запропоновані цитати/обіцянки. Схвалення і send окремі. |
| WAIT | Зберігає підписку на inbound, operator_response, permission_changed, commitment_due, outcome та/або майбутній строк. Нерелевантний inbound оновлює контекст, але не викликає LLM. |
| IGNORE | Завершує поточну увагу. Новий сигнал може створити нову увагу. |
| HANDOFF | Одразу HUMAN_OWNED, AI tasks скасовані, збережений пакет передачі й статус requested. |
| STOP | Suppression на рівні person, скасування намірів і очікувань, відкликання typed grants. Не маскується під рішення оператора. |

Послідовні inbound згортаються в одну pending engagement_evaluate task. Старий run
не може використати нову версію engagement, навіть якщо отримає її ID. Restart
зберігає WAIT без LLM-викликів. Перервані обчислення потребують явного retry або
нової події, а committed WAIT після crash не запускається вдруге через retry.

Після ACT система не викликає модель автоматично лише для створення WAIT.
Delivered action зберігає історію, obligations і expected_next; наступна увага
виникає через новий inbound, явну подію або строк. Це навмисно усуває цикл
«надіслати → знову подумати → знову надіслати».

## Дозволи та виконання

Типізований grant фіксує partner, person, conversation, channel/account, reply або
follow_up, grantor, evidence, valid_from, expires_at і revoked_at. Ці grants створює
тільки оператор. Автоматичної конвертації вхідного інтересу у згоду немає.

Для ACT потрібен чинний grant відповідної мети. Approval повторно перевіряє grant
і актуальність рішення. Перед send `validApproved` знову перевіряє саме grant із
рішення, його строк, ownership, suppression, контекст та людське схвалення
актуальної версії. Новий grant не відновлює старе рішення. Дані approval не є
permission. Режим AUTOPILOT не працює для розмов, увімкнених у цьому контурі.

Обидва існуючі transport adapters проходять через `validApproved`; їхній код не
переписано. Bot API adapter перевірено із синтетичною функцією мережевого виклику.
Живий Bot API і GramJS у цьому середовищі не перевірялися. Транзакція не може
скасувати зовнішню відправку, яка вже почалася; затриманий STOP обробляється після
наявної service.exclusive межі. Втрачена відповідь провайдера залишається unknown,
а не автоматичним success/failure і не підставою для повторного send.

Це фундамент контактних дозволів, не універсальний ACL, не юридична оцінка згоди,
не permission для обробки персональних даних і не permission для нових каналів.

## Людські правки, learning і приватність

explained та commitments повинні бути точними фрагментами запропонованого тексту.
До реальної доставки вони не підтверджені. Якщо оператор змінив draft, модельні
цитати й обіцянки не переносяться автоматично навіть після доставки. Оператор може
зафіксувати фактично надіслану цитату через explanation.record / commitment.record.
Старі та нові версії тексту, approvals, attempts і фактичні messages залишаються
окремими. В episode відображається human_assisted association, якщо draft редагували.

Candidate lesson потребує хоча б одного реально записаного й пов’язаного outcome.
Review зберігає оцінку, обмеження та локальні counterexample outcome IDs. Активація
створює нову версію стратегії, стара стає retired. Це людське рішення допустити
обмежену інструкцію, а не автоматична статистична сертифікація навички. Один outcome
не доводить покращення рекрутингу. Старий lesson.review не обходить цей review для
структурованих кандидатів.

Стратегії у v1 доступні тільки в тій самій розмові. Cross-person learning потребує
окремого механізму знеособлення, оцінки й експериментів; його тут немає. Snapshots
містять персональні дані. Архівуйте й експортуйте робочу БД відповідно до її рівня
чутливості. Нова автентифікація, шифрування та retention policy не додані.

## Операторський workflow

У картці людини є панель «Постійна справа»: відкриття, поточна потреба, невідоме,
beliefs, очікування, commitments, handoff, grants, журнал рішень і JSON episode.
Звичайні кнопки схвалення/редагування/доставки залишилися. «Свой черновик» у
керованій розмові веде до ACT, а не обходить рішення. «Результаты» дозволяють
пов’язати outcome з рішенням. На вкладці досвіду для controlled lessons з’являється
review з оцінкою та обмеженнями замість прямої активації.

Відомі UX-межі: поля часу grant використовують ISO timestamp; деякі деталізовані
операції потребують ID; старий інтерфейс лишився російськомовним, нова панель
українськомовна. Це функціональний операторський зріз, не повний UI redesign.
Немає окремого UI для всіх belief/commitment команд; вони доступні через API.

## Узгодження зі старим Cognitive Loop Review

COGNITIVE_LOOP_REVIEW.md залишається історичним аналізом. Його намір реалізовано через
єдиний EngagementLoop поверх існуючого service. Немає нового router для приватних
діалогів, другого datastore або паралельного sent-state. Public Opportunity/Router
продовжує свій read-only режим і не отримує контактних прав через нові таблиці.

SQLite, його транзакції/FK/FTS, чинні JSON contracts і Node test runner використано
повторно. Нових npm/Python dependencies немає. Generic infrastructure не переписано.
Мікросервіси, vector DB, swarm, self-modifying code, RL, fine-tuning і нові соцмережі
до increment не входять.
