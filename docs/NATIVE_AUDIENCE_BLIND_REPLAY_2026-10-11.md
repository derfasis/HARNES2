# Native Audience blind replay — real calls, synthetic discussions

The runtime barrier is resolved. Four frozen commercial-task discussions and
ten pre-existing RepoLab discussions traversed the **actual HARNES → pinned
Hermes → local CLIProxyAPI route**. All fourteen returned HTTP 200, exited cleanly,
applied the typed contract to current source bases and closed their test grants.
No contact, conversation, draft, delivery, work-transfer or action record was created.

This establishes a working bounded reasoning route. It does **not** establish
recruitment usefulness, FitLine suitability, current active intent or contact consent.
Strict semantic fidelity is **FAIL: 10 acceptable / 4 defective interpretations**.
The outputs remain unverified hypotheses for review.

## What changed to make the actual route work

Owner admitted the shared-service maintenance window. Official CLIProxyAPI v8.0.23
replaced the default public executable; the original private config stayed
byte-identical and the Python adapter/ZCode editor were preserved. One isolated
native admission stopped before dispatch because its exact catalog token was not
published at that check; publication timing/root cause is unknown. The standing
service recovered with its configured alias catalog.

The first standing-service HARNES attempt was rejected **locally** by the strict
JSON gateway before any upstream forward: pinned Hermes preferred streaming.
The no-tools worker now supplies Hermes' existing `model.streaming: false`
setting. No upstream Hermes patch, alternate runtime, credentials migration or
stream parser was introduced. The actual-worker/SDK loopback controls reject
streaming, accept valid JSON, retain usage and enforce the request cap on empty
responses.

The next conformance call succeeded: HTTP 200, child exit 0, native
`proposal_created`, receipt and exact quotes valid. A one-off diagnostic verifier
incorrectly compared a typed model-identity object with a string and initially
printed BLOCKED. An independently saved **posthoc receipt-bound audit** verified
the original gateway/report/ledger/SQLite/run identity without a new call or
rewriting the terminal result. This diagnostic error is not hidden as a historical
PASS. The actual live-ledger cap is consumed; it must not be reset or rerun.

## Experiment design

Both datasets, canonical prompt and independent gold were frozen before their
calls. Gold was never supplied to inference. The four original cases and stopped
Stage0 manifest/ledger remain unchanged. The new four- and ten-cell admissions
use separate namespaces, finite consumed reservations and no automatic retry.

| Group | Objective | Source |
| --- | --- | --- |
| Four RU/UA cases | Understand the author's own commercial task, conditions and later status; prepare an internal brief | Existing `benchmarks/commercial-task-fidelity-v1` synthetic cases and independent gold |
| Ten RepoLab cases | Find personally stated third-party goods/commission or own-client assortment intent; distinguish supplier, quote, vacancy, ambiguity and withdrawal | Exact prior `audience-a-control-v1` fixture: 53 synthetic messages, original authors/IDs/dates/replies |

These objectives differ. There was no arm B, no prompt tuning between cells and
**no causal A/B comparison**. Source capture clocks and domain-generated IDs are
truthfully recorded, not changed to manufacture parity. Current ingestion evidence
does not prove a person still wants something today.

The checked-out code includes only the reviewed nonstream worker extension on
canonical `main@d74329d7c027c2cf1a924788ff57fcd3370ac6a9` plus the previously
prepared experiment. The retained historic Stage0 freeze intentionally does not
claim to describe today's changed worker. CLI unit fixtures refresh only their
isolated copied worker hash; no consumed real ledger or original freeze was reset.

On the **ten constructed RepoLab stated-intent cases only**: TP=4, TN=6, FP=0,
FN=0 (sample precision/recall 1.0). This is a local role-recognition result, not a
market estimate or proof of four currently “hot” prospects. The four commercial
task cases use a different objective and are not added to that confusion matrix.

The useful failure pattern is now concrete: models recognize authors, quotes and
withdrawals better than they preserve temporal qualifiers, alternative lineage and
UNKNOWN commercial fit. A valid JSON response and exact quotation do not guarantee
a faithful conclusion. Review must inspect the material itself.

Independent Luna review supplied adversarial criticism; root checked it against
the actual contract before adopting findings. Two proposed issues were rejected:
`support_quotes` intentionally covers evidence **and selected context/counterevidence**;
and `prepare_material` is an inert internal brief, not an active contact/action.
The clearly closed UA4 historical brief is valid under its understanding objective.
Downstream counting all `needs_proposed` as active opportunities would be wrong.

## Verification and next practical step

Combined production-code gate: **1660 Node + 25 Python + build PASS**; the build
checked 262 JS/JSON and 11 Python files. Focused copied-fixture/UI controls: 20/20
PASS. Actual worker/SDK nonstream/request-budget controls: 2/2 PASS, included in
the 25 Python tests. `git diff --check` passes. Hosted verification for a previous
head must not be substituted for CI on the next commit.

This is sufficient to move to a **read-only, operator-reviewed real-data pilot**,
not unattended outreach. The next practical test is a fixed chronological sample
of 20 complete available discussions from already approved sources, including
ordinary negatives. Freeze the selection before inference, retain author/date/
reply/quote evidence, inspect both proposed and rejected cases, and record missing
history. Do not silently select only impressive hits or call no-result a solved need.

Leave commercial intent, last stated status, offer fit and contact authority
separate. No automatic sends, new contact permission or default-on runtime follow
from this report. The precision/recall of real retrieval, ongoing monitoring,
owner usefulness and economic scalability remain untested.
