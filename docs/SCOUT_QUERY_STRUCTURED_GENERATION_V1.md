# Scoped Scout query: constrained generation

The real native query run `1565fb09-f68e-4c8a-a8de-2eaa50365d51` reached Gemini through the configured CLIProxy but failed `SCOUT_JSON_INVALID`. No proposal was accepted and semantic quality was not evaluated. Asking for JSON in a prompt did not establish a reliable generation contract.

The existing no-tool worker now passes the frozen query `output_contract` to the provider using the public pinned-Hermes `AIAgent(request_overrides=...)` option. It sends `extra_body.response_format = {type: json_schema, json_schema: {name: scout_query_intent, strict: true, schema: ...}}` only for **scoped Scout query receipts using custom/chat_completions**. History assessments, ordinary Router calls, private conversations and other API modes retain their previous wire contracts. No upstream Hermes source or license changes are needed; the pin remains `4810074d73d9419dc82545202d595507a73f4f0e`.

This is generation assistance, not an acceptance or authority boundary. The parent still verifies the exact immutable request, profile, packet and schema digest before dispatch; raw JSON parsing, Ajv, literal source projection, ancestry, freshness and revocation checks remain unchanged. The worker never repairs a response, uses a tolerant parser, treats provider compliance as truth or grants contact permission. Provider rejection remains a failed one-attempt run, with no free-form fallback.

## Compatibility and verification

The installed proxy binary matches the local 8.0.23 binary and embeds upstream commit `d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5`. That revision maps the field to [Antigravity responseSchema](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/internal/translator/antigravity/openai/chat-completions/antigravity_openai_request.go) and [Gemini responseJsonSchema](https://github.com/router-for-me/CLIProxyAPI/blob/d318bcc3afb9ea8782862f5e8cdb541afdc9dfa5/internal/translator/gemini/openai/chat-completions/gemini_openai_request.go). These are observations about this installation, not a universal guarantee for arbitrary custom endpoints. Unsupported schema features may be rejected or omitted by a provider/proxy; the original HARNES2 validator remains authoritative.

`tests/test_scout_query_generation.py` launches the actual worker and pinned Hermes against a loopback HTTP fixture. It proves the full original schema reaches `/v1/chat/completions`, raw malformed/schema-invalid text is unchanged, HTTP 400 never purchases another generation or drops the format, and historical assessment requests omit the new field. Unit cases cover other transports and missing query contracts. These tests do not prove remote model semantics or backend enforcement. The existing immutable worker blob pin is updated to this tested extension; other frozen pins are unchanged.

The successful configured-proxy call is one conformance observation, not a fleet guarantee.
