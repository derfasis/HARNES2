# Концепция продукта: Digital AI Partner

## 1. Главная идея

Я хочу создать не обычного AI-бота, не узкого AI-SDR и не просто «ИИ-сотрудника на одну функцию».

Моя идея — **Digital AI Partner**: постоянный цифровой партнёр по развитию бизнеса, который со временем обрастает новыми способностями, каналами и опытом.

Первый use case — рекрутинг партнёров в сетевом бизнесе / MLM. Первый тестовый оффер можно считать PM-International / FitLine. Но сам продукт должен быть шире конкретного оффера.

Цель — создать одного действительно сильного AI-партнёра, который работает как самостоятельный участник бизнеса:

- ищет потенциально подходящих людей;
- анализирует разрешённый публичный контекст;
- понимает, кому вообще стоит писать;
- начинает естественный персональный диалог;
- ведёт разговор;
- квалифицирует интерес;
- делает follow-up;
- передаёт сильного кандидата человеку на звонок;
- помнит прошлое взаимодействие;
- использует собственный накопленный опыт;
- постепенно получает новые «руки и ноги»: email, browser, social media, calendar, research и другие инструменты.

Это не должна быть система из десятка разрозненных ботов. Это должен быть **один постоянный AI-партнёр с общей целью, памятью, опытом и набором подключаемых способностей**.

## 3. Почему мне интересны agent runtimes типа OpenClaw / Hermes

Я не хочу с нуля писать весь agent runtime.

Уже существуют open-source системы, которые умеют:

- работать как постоянный агент;
- иметь identity / soul / memory;
- использовать tools;
- подключать skills;
- работать с браузером;
- использовать MCP / plugins;
- работать по расписанию;
- сохранять состояние;
- расширяться новыми способностями;
- в некоторых случаях создавать или улучшать собственные skills.

Поэтому моя идея — **не переписывать всё с нуля**, а найти лучший существующий runtime / framework и использовать его как основу.

Например, среди кандидатов могут быть:

- OpenClaw;
- Hermes;
- другие лёгкие agent runtimes;
- отдельные open-source проекты, которые мы уже нашли.

Я отдельно приложу список найденных репозиториев.

Мне важно, чтобы ты не принимал OpenClaw или Hermes как заранее выбранную основу.

Нужно критически определить:

> какой существующий open-source runtime лучше всего подходит как «тело» для Digital AI Partner?

Или, возможно:

> какие части стоит взять готовыми, а какое небольшое собственное ядро написать поверх них?

## 4. Главное архитектурное требование

Я не хочу, чтобы продукт навсегда зависел от одного конкретного runtime.

В идеале:

```text
              DIGITAL AI PARTNER
                     │
       ┌─────────────┴─────────────┐
       │                           │
  PARTNER CORE                BUSINESS STATE
 identity / goal              CRM / outcomes
 memory / experience          contacts / tasks
 knowledge                    conversations
       │                           │
       └─────────────┬─────────────┘
                     │
                AGENT RUNTIME
           OpenClaw / Hermes / другой
                     │
               CAPABILITIES
       Telegram / Gmail / Browser /
       Social / Calendar / Research
```

То есть **партнёр должен пережить смену оболочки**.

Если через полгода появится runtime лучше OpenClaw или Hermes, мы должны иметь возможность заменить runtime, не потеряв:

- identity;
- memory;
- experience;
- business state;
- outcomes;
- knowledge;
- tool contracts.

## 5. Это не «AI-раб», а AI-партнёр

Мне принципиально нравится именно эта идея.

Не:

> «Вот ИИ. Дай ему задачу, он её выполнит.»

А:

> «Вот мой цифровой партнёр. У него есть постоянная цель — помогать развивать бизнес.»

Он должен уметь сам видеть рабочие задачи внутри разрешённых границ.

Например:

```text
Утром:
- проверить follow-up в Telegram;
- посмотреть новые входящие;
- обработать ответы на email;
- найти несколько новых релевантных контактов;
- проверить ответы на публикации.

Днём:
- продолжить диалоги;
- подготовить контент;
- исследовать новый источник трафика;
- передать горячего кандидата человеку.

Вечером:
- обновить результаты;
- отметить зависшие разговоры;
- подготовить следующие действия.
```

То есть это должен быть **микро-живущий рабочий организм**, а не функция `send_message()`.

---

## 6. Саморазвитие и новые skills

Мне особенно интересна способность агента постепенно улучшать собственный рабочий инструментарий.

Например:

```text
Agent:
«Мне не хватает способности X для работы с этим каналом.»

↓
создаёт / адаптирует skill

↓
проверяет его в sandbox / tests

↓
после разрешения получает новую способность

↓
использует её дальше
```

Я не хочу давать агенту бесконтрольное право ставить и запускать что угодно.

Но хочу архитектуру, в которой **агент может замечать capability gaps и предлагать / создавать новые skills**.

То есть продукт должен быть способен **обрастать новыми органами**, а не требовать каждый раз вручную переписывать архитектуру.

---

## 7. Мозг и интеллект

Я не хочу превращать сильную LLM в деревянного робота огромным system prompt.

Моя гипотеза:

```text
Strong base model
        +
thin identity / goals / hard boundaries
        +
knowledge
        +
memory
        +
experience
        +
current person context
        +
tools
        ↓
самостоятельное профессиональное решение
```

Модель должна сама хорошо рассуждать.

Мы не должны прописывать 200 правил вида:

- на первой стадии скажи X;
- если человек сказал Y — отправь Z;
- после двух сообщений предложи звонок.

Я хочу сохранить максимально много интеллекта самой сильной модели.

Жёсткими должны быть только реальные ограничения:

- не врать;
- не придумывать личность;
- не скрывать компанию при прямом вопросе;
- не давать неподтверждённые обещания;
- не давить после отказа;
- не нарушать permissions;
- не выполнять опасные действия без нужного уровня контроля.

---

## 8. Память и «имитация опыта»

Мне интересен эффект, при котором AI-партнёр со временем становится опытнее.

Я понимаю, что vector memory не меняет веса модели.

Но хочу использовать внешний накопленный опыт:

```text
conversation
→ decision
→ action
→ human correction
→ reply
→ outcome
→ lesson
→ storage

Новая похожая ситуация
→ retrieval релевантного опыта
→ LLM учитывает его
→ новое решение
```

Таким образом партнёр может вести себя так, будто «он уже сотни раз видел похожую ситуацию».

Но я не хочу заранее навязывать vector DB.

Нужно определить:

- где достаточно SQL;
- где нужна structured memory;
- где нужен semantic retrieval;
- когда появляется реальная необходимость embeddings / vector search;
- как не превратить память в свалку мусора;
- как отделять реальный опыт от случайной корреляции.

## 9. Самый ценный будущий актив

Я считаю, что главным moat может стать не runtime и не prompt, а наш собственный outcome dataset:

```text
person/context
+ source
+ decision
+ approach
+ draft
+ human edit
+ actually sent message
+ reply / ignore / negative
+ objections
+ qualified
+ booked call
+ show
+ joined
+ cost
+ lesson
```

Особенно важно сохранять attribution.

Если AI написал плохое сообщение, человек его полностью переписал, а потом кандидат вступил — нельзя записывать это как успех исходной версии AI.

Я хочу, чтобы система реально могла понимать:

> что было сделано самой моделью, что изменил человек и что в итоге дало результат.

Потенциальные capability modules:

- social media publishing;
- inbound replies;
- content creation;
- calendar;
- booking;
- CRM;
- analytics;
- lead research;
- knowledge research.

Каждый канал должен подключаться как новая способность одного партнёра.

Не хочу строить десять отдельных продуктов для десяти каналов.

## 11. Социальные сети

Отдельно мне интересна идея, что AI-партнёр может полноценно вести свою рабочую social presence:

- создавать контент;
- генерировать изображения;
- готовить публикации;
- отвечать на входящие;
- видеть интерес;
- квалифицировать;
- переводить человека на следующий шаг.

Это может стать отдельным каналом органического трафика.

Но я не хочу строить обманную «фальшивую человеческую жизнь».

Если используется persistent persona, она должна быть прозрачной и не выдавать AI за конкретного реального человека.

---

## 12. Экономика важнее красоты архитектуры

Финальный критерий — не количество tools и не размер memory.

Например:

```text
AI Partner cost:
$10 / неделю

Результат:
5 qualified conversations
2 calls
1 joined partner
$100+ business value
```

Тогда система экономически имеет смысл.

Если очень лёгкий агент стоит $2, но никого не приводит — он хуже.

Поэтому при сравнении runtimes нужно смотреть не только:

- latency;
- tokens;
- context size;
- RAM;
- stability;

но и:

- useful conversations;
- qualified leads;
- booked calls;
- joined;
- human intervention;
- cost per qualified;
- cost per joined;
- revenue / cost ratio.

## 13. Что я НЕ хочу делать

Не хочу:

- писать огромный agent runtime с нуля, если можно использовать зрелую основу;
- делать Frankenstein из пяти несовместимых runtimes;
- заранее строить multi-agent organization;
- добавлять vector DB «потому что модно»;
- делать сложные микросервисы без необходимости;
- строить account farms;
- обходить антиспам-защиту;
- делать proxy evasion;
- выдавать AI за конкретного живого человека;
- превращать систему в массовый spam machine.

Если сформулировать идею одной фразой:

> **Я хочу создать не AI-работника на одну задачу, а постоянного Digital AI Partner — цифрового партнёра, который имеет общую цель, память, опыт и постепенно обрастает новыми инструментами и каналами, используя готовый open-source agent runtime как основу, а не создавая всё с нуля.**

Первый его навык:

> **Recruiting.**

Первый рабочий канал:

> **Telegram.**

Но конечная цель:

> **универсальный цифровой партнёр по развитию бизнеса.**
